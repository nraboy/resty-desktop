# Restic Integration

Read this before: adding a new restic subprocess call, touching backend credentials
(S3/B2/REST), read-only-repo (`--no-lock`) handling, or the stats cache.
Linked from CLAUDE.md's Restic Integration summary.

## Restic Integration

- Restic binary path is user-configurable; defaults to `restic` on `$PATH`.
- All commands set `RESTIC_REPOSITORY` and `RESTIC_PASSWORD` env vars — never pass either in process args.
- Every restic `Command` sets `.stdin(Stdio::null())` alongside `.no_console()` (`mod.rs`'s `NoConsole` trait). Without it, stdin defaults to `Stdio::inherit()`, which in a windowless Tauri app on Windows can be an invalid handle; process wrappers that do their own internal `CreateProcess` (e.g. Scoop shims) can fail to spawn the real binary when handed that invalid inherited handle ("Could not create process" errors, unrelated to restic/SSH/SFTP config). Any new restic `Command` must set `.stdin(Stdio::null())` too.
- All restic subprocess calls run off the async runtime: streaming commands spawn a `Child` inside `tauri::async_runtime::spawn_blocking` (e.g. `execute_backup`, `restore_snapshot`, `copy_snapshot`, `mirror_repo`); one-shot commands go through `run_restic_blocking` (`repo.rs`), which does the same for a single `Command::output()` call. `prune_all_repos`/`prune_repo` are the one exception to the "spawn inside `spawn_blocking`" pattern: they spawn their `Child` inline with null stdio and poll it via `try_wait` + `tokio::time::sleep` in short lock windows, so `cancel_prune` is never blocked waiting on the mutex — this is intentional, not a gap. Their cancel-path `restic unlock` (clearing the lock after a kill) goes through `run_restic_blocking` like every other one-shot call. An `async fn` `#[tauri::command]` must never call `std::process::Command` (or `run_restic_with_path`) inline — that blocks a shared tokio worker and starves every other async command and the `AppDb` lock (see Persistence & Caching). Plain `run_restic_with_path` is still called directly from code that's already inside a `spawn_blocking` closure (e.g. `run_full_index`) — that's correct as-is, not a gap.
- `restic ls --json` outputs NDJSON; first line is snapshot summary (skipped); subsequent lines are `FileEntry`.
- `execute_backup` streams NDJSON line-by-line; `status` lines → `backup:progress` events; `summary` line captured and returned; `error` lines are ignored — restic ≥0.17 (this app's minimum supported version) always exits non-zero when any source file is unreadable, so a run with `error` lines never reaches the success path (see CLAUDE.md's Settled decisions on why there's no "Warnings" notification category). Reads compression from `app_settings` (`RESTIC_COMPRESSION` env). Accepts `limit_upload`/`limit_download` (KiB/s); `Some(0)` treated as `None`. Also accepts `excludes` (`--exclude`), `exclude_if_present` (`--exclude-if-present`, one flag per marker filename — restic excludes a matched directory's *contents*, not the marker file itself) and `exclude_caches` (`--exclude-caches`); all three are built by the pure, unit-tested `build_exclude_args` helper (`snapshot.rs`), which applies the same trim/blank/`#`-comment filtering to both `excludes` and `exclude_if_present`. Serialized via a `busy` flag on `BackupHandle` — only one backup runs at a time; a concurrent attempt (e.g. a scheduler tick firing during a manual backup) returns `"A backup is already in progress"` and fires **no** notification (this pre-flight rejection is a routine collision, not a failure worth surfacing — don't add one). Sequential callers (`run_schedule_now`, scheduler loop) are unaffected since each `await` releases the flag before the next starts. On a genuine cancellation (`BackupHandle::cancelled` set), the `Err` branch logs `CANCELLED_BACKUP_ERROR` ("Cancelled") to `backup_history` instead of the raw `"cancelled"` control-flow string, and fires a "Backup cancelled" notification instead of "Backup failed" — see `CANCELLED_BACKUP_ERROR` in `lib/types.ts` and `LogsPage`/`ActivityPanel`'s matching neutral rendering.

  **Notifications** (`commands/notify.rs`) are gated by four global `app_settings` toggles
  (`notify_started`/`notify_success_changed`/`notify_success_unchanged`/`notify_failures`,
  defaults off/on/off/on), read via `notify::load`, which fetches all four
  under one `AppDb::get_settings` call (a single mutex acquisition/query, not four) — worth
  keeping in mind before adding a fifth category or another `load()` call site, since each call
  still takes the shared `AppDb` mutex once. `notify::notify(app, db, category, title, body)` is
  the single gated entry point every `.show()` in `execute_backup` goes through — it loads the
  settings itself and skips the `.show()` when the category is muted. Gating only ever skips the
  `.show()` itself, never `db.log_backup`, `backup:history-updated`, or the `task` bus, so a muted
  category still shows up in Recent Logs and the Activity panel. A successful (exit 0) run
  is classified by the pure, unit-tested `notify::classify_success(files_new, files_changed)`:
  `files_new + files_changed > 0` → SuccessChanged; else SuccessUnchanged (deliberately not
  consulting `data_added`/dir counts, which restic can report nonzero on a genuine no-op run).
  Read-only rejection and a real restic failure
  both map to Failures, same as a cancellation. The "Backup started" notification body is the
  repo's **name**
  (`AppDb::get_repo_name`, a dedicated single-column lookup), never `repo.path`/`FullRepository` —
  a REST repo's path can carry inline userinfo credentials (`rest:https://user:PASS@host/repo`,
  see the Restic Integration REST paragraph), which must never reach an OS notification; falls
  back to the opaque `repo_id` if the name lookup fails.
- `cancel_backup`, `cancel_copy`, `cancel_mirror`, `cancel_prune`, `cancel_restore` all run `restic unlock` after SIGKILL to clear stale locks.
- `copy_snapshot` runs `restic copy --from-repo <src> <snapshot_id>` against the destination repo.
- `mirror_repo` uses `RESTIC_FROM_REPOSITORY`/`RESTIC_FROM_PASSWORD` env vars to copy all snapshots src→dest. Queued rather than single-in-flight (see `MirrorHandle`/`MirrorEntry`, `cache.rs`, and the Operation Event Bus section's mirror paragraph): the command registers the run and returns its `operationId` immediately — the actual copy runs in a detached `spawn`ed task, waiting its turn on `MirrorHandle::turn` (a FIFO lane; only one `restic copy` process runs at a time) before executing. Multiple mirrors can be queued at once, including two into the same destination from different sources; only an exact `(src_repo_id, dest_repo_id)` repeat already queued or running is rejected (`MIRROR_ALREADY_ACTIVE_ERROR`), checked and registered atomically under one lock acquisition. `cancel_mirror(operation_id)` targets one run by id — a still-queued run is woken via `MirrorEntry::cancel_notify` and never spawns; a running one is SIGKILLed, with the `restic unlock` on both repos happening in the task's own cancelled-branch handling once `wait()` confirms the process exited (same "kill in `cancel_*`, unlock in the operation's own post-kill handling" pattern `cancel_backup`/`cancel_copy` already follow).
- `diff_snapshots` parses plain-text `restic diff` output (no `--json`); prefixes `+`/`-`/`M`/`T`; capped at 500 entries with `truncated` flag. DiffPage always navigates older→newer so `+` = added in newer.
- `check_repo` runs `restic check --json`; duration measured via `Instant` (no timing in summary). Returns `CheckResult { success, errors, duration_seconds }`.
- `restore_snapshot` streams `restic restore --json`; emits `restore:progress` events. Stderr drained on background thread. Serialized via a `busy` flag on `RestoreHandle` (same pattern as `BackupHandle`) — a concurrent attempt returns `"A restore is already in progress"`. Cancellable via `cancel_restore`; on cancel, a successful exit still wins over the cancelled flag (handles the race where Stop is clicked right as the restore finishes).
- `unlock_app` runs `restic unlock` on all repos in background after password verified.
- A repository can be marked **read-only** (`Repository.read_only` / `FullRepository.read_only`) for repos backed by a genuinely read-only filesystem or mount. `repo::apply_repo_flags`/`apply_from_repo_flags` (extending `apply_repo_password`/`apply_from_repo_password`) append restic's own `--no-lock` flag whenever the repo is read-only — this is the single choke point every read-type call goes through (`run_restic_with_path`, `check_repo`, `prune`), so no other call site needs to know about it. Every write-type command (`execute_backup`, `delete_snapshot`, `tag_snapshot`, `apply_retention`, `prune_repo`/`prune_all_repos`, `unlock_repo`, and `copy_snapshot`/`mirror_repo` on the **destination** side) instead calls `repo::ensure_writable(&repo)` immediately after resolving the `FullRepository` and refuses with `READ_ONLY_REPO_ERROR` — restic's own lock semantics make `--no-lock` safe only for reads, so a write path is refused outright rather than relying on restic to reject it. A read-only repo may still be a mirror/copy **source** (`apply_from_repo_flags` on the `--from-repo` side) — restic's `copy` opens the source under `--no-lock` and the destination normally, so rescuing snapshots off a read-only archive into a writable repo works. `prune_all_repos` skips read-only repos rather than failing the batch. Cancel-path `restic unlock` calls (and the `unlock_app` sweep) are skipped for a read-only repo — it was opened with `--no-lock`, so it never held a lock to clear, and the unlock's own delete would fail against a genuinely read-only backing store.
- **Backend credentials.** A repository may carry per-backend credentials (e.g. `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` for S3, `B2_ACCOUNT_ID`/`B2_ACCOUNT_KEY` for native Backblaze B2), encrypted under the master key alongside the repo password (`FullRepository.credentials: Vec<Credential>`, `commands/backends.rs` for the registry). **Empty credentials is the ambient mode every pre-existing repo is in and stays in** unless the user explicitly stores credentials: with none stored, restic falls back to its own credential chain (env inherited from the app process, `~/.aws/credentials`, an IAM role) exactly as it always has — the app was setting no backend env vars at all before this feature existed, so this had to be additive-only, not a silent behavior change for existing S3 repos. `repo::apply_backend_env` sets each stored credential as an env var and is called from both `apply_repo_flags`/`apply_from_repo_flags` (covering `run_restic_with_path`/`run_restic_blocking`, `check_repo`, `run_one_prune_attempt`) and from five call sites that build their `Command` inline inside a `spawn_blocking` closure (`execute_backup`, `restore_snapshot`, `copy_snapshot`, `mirror_repo`'s destination side, `run_full_index`'s two callers) rather than going through those helpers; each of those clones the whole `FullRepository` (never rebuilds one field-by-field) specifically so credentials aren't silently dropped — see `repo::unlock_quietly`'s doc comment, which replaced eight hand-built cancel-path `FullRepository { .. }` unlock literals with one helper for the same reason. A credential with an empty value is skipped rather than set as `""`, since `AWS_ACCESS_KEY_ID=""` would *break* the ambient fallback chain rather than falling through to it. `apply_backend_env` also skips any credential whose key is reserved (`backends::is_reserved_key` — `PATH` or a `RESTIC_*` var other than the two-item `ALLOWED_RESTIC_KEYS` allowlist below) **unconditionally, regardless of apply order** — every call site sets `RESTIC_REPOSITORY` (and, for copy/mirror, `RESTIC_FROM_REPOSITORY`) on the `Command` *before* calling `apply_backend_env`, so without this guard a stored credential of one of those names would win the collision and silently redirect the operation to a different repository. `backends::validate_credentials` rejects a reserved key at entry too — the earlier, louder guard, and the one that also runs against `import_data`'s bundle-sourced credentials — but `apply_backend_env`'s own filter is what makes the guarantee hold regardless of which path a row reached the DB by (an imported bundle, a hand-edited database), not just the ones that went through `validate_credentials` first. Backend kind is **never stored** — `backends::detect_kind(path)` derives it from the path on every read, so it can never drift out of sync with an edited path (a path edit that changes the derived kind while credentials are stored is rejected client-side, `RepositoriesPage.tsx`). Backend credentials are process-wide env with **no `--from-` counterpart** (unlike the password, which has `RESTIC_FROM_PASSWORD`), so `repo::merge_credentials` pre-flight-checks `copy_snapshot`/`mirror_repo` for a same-key-different-value conflict between source and destination before either takes a `RepoLocks` guard or (for mirror) occupies `MirrorHandle::turn`'s FIFO lane — two repos on the same backend with different accounts genuinely cannot be used together in one restic process.
  - **REST backend (`rest:`).** `BackendKind::Rest` (detected like S3/B2, ahead of the generic `Other` remote-prefix match) accepts `RESTIC_REST_USERNAME`/`RESTIC_REST_PASSWORD` — both optional, `backends::REST_SPECS` — restic's own env-var alternative to inline `rest:https://user:pass@host/` userinfo. This exists because a `/`, `@`, `?`, or `#` inside an inline REST password breaks Go's `net/url` parsing (`rest:https://user:pass/word@host` parses as host `user`, port `pass`, producing restic's `invalid port ":pass" after host`); percent-encoding the password is the literal fix and still works, but storing the credential as these two env vars avoids it and keeps the password out of the plaintext `repositories.path` column. `backends::is_reserved_key`'s `ALLOWED_RESTIC_KEYS` allowlists exactly these two `RESTIC_*` names — safe unconditionally (not just for `Rest`) because the app itself never sets either, so there is no collision for a stored value to win, unlike `RESTIC_REPOSITORY`/`RESTIC_PASSWORD`/`RESTIC_FROM_*`/`RESTIC_COMPRESSION`. Unlike S3/B2, `Rest` deliberately still accepts arbitrary unrecognized keys (see docs/decisions.md) — every `rest:` repo added before this variant existed was `BackendKind::Other`, which has no unknown-key check, and may already store one. **restic reads only the unprefixed `RESTIC_REST_USERNAME`/`_PASSWORD` for both the primary and a copy/mirror's `--from-repo`** (`ApplyEnvironment("")`, restic v0.17.3–v0.19.1 verified — the sole call site in both, `cmd/restic/global.go`/`internal/global/global.go`) — there is no `RESTIC_FROM_RESTIC_REST_*` counterpart, so a REST repo on either side of a copy/mirror needs no special handling beyond the existing `merge_credentials` conflict check. Also note: **inline URL userinfo always wins over the env vars** — restic's `ApplyEnvironment` only reads them when the URL has neither a username nor a password set, with no merge and no warning when it ignores them — so `RepositoriesPage.tsx`'s add/edit forms show a second, neutral hint (`hasInlineRestUserinfo`) when a `rest:` path already has inline credentials and credential rows are also filled in, alongside the amber `hasBrokenRestUserinfo` hint for the URL-breaking case itself (both in `src/lib/backends.ts`, both advisory only — neither blocks Save or Test Connection).
- Stats cache (`repo_stats_cache`) is **never auto-evicted** — not after backup, forget/retention, copy, mirror, or snapshot delete. It only changes via the Refresh row/Refresh All buttons on RepositoriesPage (`refresh_repo_stats`), which is a deliberate, user-driven-only model (the previous event-driven eviction made the page feel like it "refreshed at random" — same page, different states, for reasons the user never triggered). A failed refresh leaves the last-good cached value in place. Each row shows the cached value's `cached_at` as a "Refreshed …" label (see `ResticStats.cached_at`, `repo_stats_cache.cached_at`).
- `fetch_and_cache_stats` runs `restic stats --json` **twice** per refresh, under the same `RepoLocks` read guard: once with restic's default mode (restore-size — logical size if everything were restored, `ResticStats.total_size`), then again with `--mode raw-data` (on-disk stored size after dedup and compression, `ResticStats.raw_size`), parsed by the separate `parse_raw_data_size` (kept apart from `parse_stats_json` since the latter is shared with `get_snapshot_stats` in snapshot.rs, which never uses raw-data mode). The raw-data call's failure is **deliberately non-fatal**: it's logged, `raw_size` is left `None` for that cycle, and the refresh still succeeds and caches the restore-size figures — making it fatal would turn an older-restic-binary or transient-remote-backend hiccup into a full "refresh failed" that blanks out numbers the user already had. `raw_size` is nullable in `repo_stats_cache`; a `NULL` (legacy row, or a cycle where raw-data failed) makes RepositoriesPage fall back to its pre-existing single-size display (`formatRepoSize` in `lib/format.ts`). `--mode raw-data` was chosen over a local filesystem walk (`du`) because it works identically for remote repos (S3/B2/REST/SFTP) — see docs/decisions.md.
